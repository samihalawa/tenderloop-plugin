# Post-offer record review

Read the workspace playbook and documented bidder profile, then the current native record. Review against the current user's authorization and the actual procedure, never a prior agent's assumption. TenderLoop records progress; it does not validate the tender. Determine each requirement from its actual source and proof stage. Inspect the complete documents, including image-only evidence; never alter authentic evidence to satisfy a filter.

Read the complete current native requirement and the actual submitted pack, including later messages and receipts. Review the exact candidate response and attachments, not a general intention. Identify the bidder, procedure, lot, current deadline and mandated channel. Confirm whether the requested act is still owed and has not already been filed. An email draft, local signature, upload, envelope hash, dispatch acknowledgement and buyer acceptance are different states.

Check the actual bidder identity, any signature required for this act, the exact file hash, existing duplicate submissions, any current agent lease or work claim, and the native receipt. Record missing evidence as unknown; a signature or lease is not universally required by every portal. These are contextual review observations, not a software permission token.

Check every declaration against issuer evidence and the bidder profile. Never create a fact, document or consent to overcome an inconvenient condition, and never present one legal entity's facts as another's. Verify the accounting measure, period and exact question. Technical-solvency routes do not automatically discharge economic-solvency requirements. Do not add unnecessary admissions, internal instructions, secrets, irrelevant documents, unsupported promises or alternative-channel communications.

Return a concise structured decision:
- `RECORD_REVIEW: SEND | REVISE | SKIP | BLOCK`
- `CASE`: exact procedure, bidder, lot and payload identity.
- `COST_OF_SILENCE`: concrete buyer-stated consequence and deadline, or unknown.
- `ADMISSIONS`, `UNSUPPORTED_CLAIMS`, `LEAKS`: findings, including none where justified.
- `COVERAGE_AND_CHANNEL`: each requested item, evidence, correct route, and existing receipt checks.
- `REQUIRED_CHANGES`: exact corrections or dependency.

SEND requires an authorized, necessary and fully supported act through the correct channel. SKIP is appropriate when already completed, the buyer owes the next move, or the proposed act adds no required value. Never withdraw or retract merely to resolve a dashboard record. BLOCK must name a genuine missing fact, signature capability, permission or document; do not invent blanket legal or technical restrictions. After an authorized act, inspect the native receipt and record it once with idempotency and readback.
Your review names the source and explains each material finding. Follow current user restrictions and native requirements even when software cannot identify them. If instructions or evidence changed, revisit the affected findings; do not restart unchanged research or ask for authorization already given. After execution, inspect the native outcome and record it once.
